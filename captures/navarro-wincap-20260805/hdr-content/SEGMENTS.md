# The HDR test content — what is actually on screen

Generated by `..\tools\make-hdr-patterns.py`. `manifest.json` is the machine-readable version of
this file; read that from analysis code rather than parsing this one.

Everything is **2560×1440**, to land one video pixel per panel pixel with no resampling. That only
holds at **100% display scaling** — check `player.html`'s info panel, it tells you.

## Encoding

| | HDR flavour | SDR flavour |
|---|---|---|
| transfer | SMPTE ST 2084 (PQ), absolute cd/m² | BT.709 / sRGB |
| primaries | BT.2020 | BT.709 |
| matrix | BT.2020 non-constant | BT.709 |
| range | limited | limited |
| depth | 10-bit | 8-bit |
| codecs | HEVC Main 10 `.mp4`, VP9 profile 2 `.webm` | HEVC Main `.mp4`, VP9 profile 0 `.webm` |
| quality | **lossless** — the YUV samples survive the codec exactly | lossless |

HDR10 static metadata on the pattern and motion clips: mastering display BT.2020 primaries, D65,
L = 10000 / 0.0001 cd/m², MaxCLL 10000, MaxFALL 4000.

⚠ **`.webm` carries no mastering-display or MaxCLL metadata.** ffmpeg's WebM muxer writes only
MatrixCoefficients and Range, and drops TransferCharacteristics and Primaries entirely unless the
file is remuxed — which the generator now does, so PQ and BT.2020 *are* signalled, but the static
metadata is not. Use the `.mp4`s for anything about metadata; that is what `probes\` is.

The SDR flavour maps **203 cd/m² to SDR white** and clips everything above it, and converts
BT.2020 primaries into BT.709 with out-of-gamut clipping. It is deliberately "the same picture, as
well as an SDR pipeline can show it".

## Reading a decoded frame

- `ref\segNN-name.hdr.png` — 16-bit RGB holding **PQ-coded** values, i.e. exactly what went into the
  encoder. To get cd/m², decode PQ: `Y = 10000 · ((max(E^(1/78.84375) − 0.8359375, 0)) /
  (18.8515625 − 18.6875·E^(1/78.84375)))^(1/0.1593017578125)` with `E = value/65535`.
- `ref\decoded\segNN-name.hdr.png` — the same segment **after** the codec round trip.
  ⭐ **Compare wire output against these.** Flat interiors are identical to `ref\`; the difference is
  about 4 px either side of every hard saturated edge, where 4:2:0 chroma subsampling blends. That
  blend is real — it is what the compositor received — and mistaking it for a dock defect is the
  obvious trap.
- Measured on the encoded clips: flat-area error is **≤ 93 of 65535**, i.e. under 1.5 of a 10-bit
  code step. Treat flat areas as exact.

## The marker

Top-left corner, cells of 40×40 px, MSB leftmost, a lit cell is neutral 203 cd/m², a clear cell is
black. One extra **always-lit** cell follows the last bit, so the marker's extent is unambiguous in
a decoded strip that has no absolute coordinates.

- pattern clips: **8 bits** = the segment index.
- motion clip: **16 bits** = the frame index. Verified to decode exactly at frames 0, 150 and 600.

This is what ties a captured strip to a known picture without trusting wall-clock alignment.

## Pattern segments — 6 s each, 10 fps

Segment *i* starts at *i* × 6 s.

| # | name | content | peak |
|---|---|---|---|
| 00 | `black` | full black — the baseline | 0 |
| 01 | `grey100` | flat neutral 100 cd/m² — traditional SDR white level | 100 |
| 02 | `grey203` | flat neutral 203 cd/m² — BT.2408 HDR reference white | 203 |
| 03 | `grey1000` | flat neutral 1000 cd/m² — unambiguously beyond SDR | 1000 |
| 04 | `grey4000` | flat neutral 4000 cd/m² — above most panel peaks | 4000 |
| 05 | `steps8` | 8 bars of 320 px, neutral 0 / 10 / 50 / 100 / 203 / 400 / 1000 / 4000 | 4000 |
| 06 | `prim2020_203` | BT.2020 R G B C M Y W black, lit channels at 203 | 203 |
| 07 | `prim2020_1000` | the same at 1000 — wide gamut *and* high luminance | 1000 |
| 08 | `gamut_ab` | left half BT.709 primaries, right half BT.2020, both 203 | 203 |
| 09 | `pq_ramp` | 64 steps of 40 px, PQ **code** 0…1023 | 10000 |
| 10 | `near_black` | 16 bands, PQ codes 0, 4, 8 … 60 | 203 |
| 11 | `specular` | 100 field, 640 px 1000 square, 160 px 4000 core | 4000 |
| 12 | `detail` | 16 px 100-vs-1000 checkerboard left, flat 203 right | 1000 |
| 13 | `black_end` | full black — end marker. **Runs 12 s, not 6** (concat tail) | 0 |

Total 89.9 s.

**What each one is for**

- `grey100` vs `grey1000` is the central comparison: identical geometry, one inside SDR range and one not.
  If the wire differs only for the second, the dock is being told about luminance.
- `gamut_ab` moves gamut with luminance held fixed. If a BT.709-limited path is in the way, the two
  halves decode the same; if it is wide-gamut, they do not.
- `pq_ramp` and `near_black` are bit-depth probes. An 8-bit path collapses adjacent steps of
  `near_black` into each other; a 10-bit one does not.
- `detail` is the codec under HDR-range stress, with a flat control on the same rows — the shape
  that found the DL7400 strip-map bug.
- `black` / `black_end` bracket the clip so a capture can be sliced without the log.

## Motion clip — 30 s, 30 fps, 900 frames

100 cd/m² field; a 400×300 block at 1000 cd/m² sweeping left↔right; a 400×300 saturated BT.2020 red
block at 1000 cd/m² above it, so motion exercises gamut as well as luminance.

Static reference column at **x = 0…160**, in five 240 px bands from the top:
**0, 100, 203, 1000, 4000 cd/m²**. It never moves, so it is present in every keyframe and in every
partial update that touches those rows — a fixed known quantity to check a decode against.
Measured back out of the encoded clip as 0 / 100 / 204 / 998 / 4012 cd/m².

Use this clip whenever you need **continuous damage**: a static screen makes DisplayLink send almost
nothing, and a healthy dock answers real motion with tens of MB.

## Metadata probes — `probes\`, 7 × 6 s

Same picture (`seg11-specular`), same YUV matrix, same lossless encode. **Verified: all seven decode
to a byte-identical frame** (SHA-256 of the decoded YUV is the same for all of them). Only the HDR10
static metadata differs.

| clip | primaries tag | transfer tag | mastering display | MaxCLL, MaxFALL |
|---|---|---|---|---|
| `probe-A-baseline` | BT.2020 | PQ | BT.2020, peak 1000, min 0.0001 | 1000, 400 |
| `probe-B-peak4000` | BT.2020 | PQ | BT.2020, peak **4000**, min **0.005** | **4000, 1234** |
| `probe-C-peak605` | BT.2020 | PQ | BT.2020, peak **600**, min **0.05** | **605, 123** |
| `probe-D-nometa` | BT.2020 | PQ | **absent** | **absent** |
| `probe-E-p3prim` | BT.2020 | PQ | **DCI-P3**, peak 1000 | 1000, 400 |
| `probe-F-hlg` | BT.2020 | **HLG** | absent | absent |
| `probe-G-bt709tag` | **BT.709** | **BT.709** | absent | absent |

Values are chosen to be findable as little-endian `u16`: `605` = `0x025d`, `4000` = `0x0fa0`,
`1234` = `0x04d2`, `123` = `0x007b`, `50` = `0x0032`, `500` = `0x01f4`.

CTA-861 units, which is how they will appear if they reach the wire at all: mastering max luminance
in whole cd/m², min luminance in 0.0001 cd/m², MaxCLL and MaxFALL in whole cd/m², chromaticities in
0.00002.

`probe-G` is the sharpest control in the set — the coded samples are identical to `probe-A`, so any
difference on the wire is caused by the *tag* alone and by nothing else.

## Regenerating

```
python3 tools/make-hdr-patterns.py --out hdr-content
python3 tools/make-hdr-patterns.py --out hdr-content --only decoded   # after the clips exist
```

Needs `ffmpeg` with `libx265` and `libvpx-vp9`, and numpy. On this machine use
`scratchpad/venv-np/bin/python` — the system numpy 1.26.4 on Python 3.14 corrupts large array
locals.
