# Chimera

Chimera is the open userspace service for a Revdi display connected to a Vino-supported
DisplayLink dock. It replaces the control, authentication, encoding, and USB responsibilities of
DisplayLinkManager while Revdi preserves the established EVDI userspace ABI.

Chimera compiles the kernel Vino protocol and codec sources directly. The copies under `vino/`
are generated by `../scripts/sync-kernel-sources.sh` and must not be edited by hand.

## Daemon

Build the production service without installing anything:

```sh
cargo build --release --bin chimera --features live,revdi
```

Run it only after the Revdi module is already available and the proprietary manager has released
the dock:

```sh
LD_LIBRARY_PATH=/opt/displaylink \
  cargo run --release --bin chimera --features live,revdi
```

The daemon:

1. initializes the dock and completes HDCP 2.2 authentication;
2. establishes the encrypted control session and authenticates both downstream heads;
3. fetches each connected monitor's EDID;
4. creates an owned Revdi output for each monitor;
5. applies the compositor-selected captured mode profile;
6. sends the video-arm prefix and training carrier; and
7. encodes coherent Revdi updates with Vino's kernel codec and submits them to the matching USB
   endpoint;
8. reconciles DPMS and any compatibility cursor events; and
9. can complete DDC/CI writes and reads through its userspace-only encrypted
   monitor-control tunnel when a client supplies them;
10. debounces monitor removal and recreates Revdi outputs after reattachment; and
11. rebuilds the owned dock session after transport failure.

No module loading, kernel installation, service management, or reboot is performed by Chimera.

## Offline oracle

`chimera-prove` replays captured DisplayLinkManager traffic through the same protocol sources used
by the kernel driver:

```sh
cargo run --bin chimera-prove
cargo test -p vino-chimera --all-features
```

The oracle checks byte-exact control sealing, message builders, codec records,
mode profiles, video-arm construction, userspace DDC/CI reply bounds, Revdi
pixel conversion, cursor repacking, and strip-grid padding. Hardware-dependent
operations are deliberately excluded from the automated suite.

The DPMS, cursor, DDC/CI, topology, and session-recovery paths are implemented, but the cleanup
revision has not been run against a live dock. They remain part of the hardware validation matrix.

## Source synchronization

From the Revdi repository root:

```sh
make sync KSRC=../linux
make check-sync KSRC=../linux
```

`check-sync` is read-only and fails when either the external Revdi module or Chimera's Vino source
copies differ from the authoritative kernel tree.
