# Handover — 2026-08-03

## Where this stands

The DL7400 (Navarro, `17e9:7000`) still shows **no picture**. Everything up to and including the
pipe configuration is accepted by the dock; the endpoint halts on image records.

| transfer | result |
|---|---|
| 48-byte sealed stream-open | ✅ URB status 0 |
| 1600-byte prologue — markers, pipe descriptor, ring record, decoder config | ✅ URB status 0 |
| first image records | ❌ `-EPIPE`, endpoint halted, dock usually re-enumerates at once |

Everything vino synthesises has been diffed against DLM and is **byte-identical**: the pipe

first strip, and the record offsets within the transfer (prologue at 0/32/64/400/432/464, first

## The nonce — solved

**It is something vino already constructs.** A stream's AES-CTR nonce is the RIV its own
`SKE_Send_Eks` delivered, with `byte7 ^= stream_id`. vino is the transmitter and generates that RIV
itself, so nothing needs capturing.

Measured by decrypting the control plane of `captures/navarro-dlm-modeset-20260802-005453` using
the Dl3Cmac tag as the oracle, then comparing each connector's wire RIV with the AES-CTR nonce the
live sealer used:

| stream | wire SKE RIV | id | RIV with `byte7 ^= id` | sealer key |
|---|---|---|---|---|
| link | `7d2cb66b2cd1757c` | `0x04` | `7d2cb66b2cd17578` | `709b61dd…` ✔ |
| connector 0 | `c345fe5593613901` | `0x07` | `c345fe5593613906` | `960b47bf…` ✔ |
| connector 1 | `9446c83da5fa39e3` | `0x0f` | `9446c83da5fa39ec` | `e5151879…` ✔ |
| connectors 2, 3 | `cfa01956e0edb145`, `6918593e8dc4be7d` | — | — | no monitor, no sealer built |

This is Ridge's rule generalised: Ridge xors byte 7 with `0x08 | head`, which *is* Ridge's stream
id. One rule now covers both, as `cp::stream_content_nonce(riv, stream_id)`.

⇒ The previous handover's "distinct recovered first-pipe key/RIV pair `960b47bf…`/`c345fe55…`, not
associated with Vino's per-connector SKE sealers" is **connector 0's own SKE sealer**. There is no
separate first-pipe key. `navarro.md`'s "uses the delivered RIV unchanged" was wrong.

## What was wrong and is now fixed

Each of these was a real bug, measured against captures:

1. **The DL7400 never got its own stream opening.** `submit_prompt_training()` called
   `build_arm_burst_buf()` unconditionally, so Ridge's ARM burst went out regardless of profile.
2. **Stream-open was 14 bytes and used the wrong sub.** It is 16 bytes (14-byte marker + 2 opaque)
   and goes out on `stream_id | 0x10` (`0x17` for connector 0), not the bare stream id. Both
   captured opens authenticate byte-for-byte under the derived key and nonce.
3. **`RepeaterAuth_Stream_Manage` declared the wrong stream id** (`head + 8` instead of
   `(connector << 3) | 7`), so the dock was told a different id than the nonce tweak used.
4. **`aux` on an image record is a record *type* on Navarro, not Ridge's zero-padding count.** DLM's
   image records always carry `aux=0`; `aux` of 2/4/6/8/a/c/e each name a per-frame control record.
   Writing a pad count there makes the dock read an image record as something else.
5. **Strip geometry.** Ridge lays a strip's sixteen `DIM`-square blocks 8 across × 2 down (64×16);
   the DL7400 lays them 16 across × 1 down (128×8). Same block count, same coded strip, so this is
   one parameterised codec (shifts), not a second one.
6. **Band order.** The DL7400 interlaces y bands (0, 16, 32 … then 8, 24, 40 …); Ridge is raster.
7. **Records only end at a y-band boundary on Ridge**, whose `sub` carries the band parity.
8. **Presence.** vino declared all four connectors connected with zero EDID bytes and drove
   `1920x1440@60` fallback modes into two empty sockets. A dock that answers a probe for every
   connector needs a recovered EDID as the presence signal.
9. **Finalize was hardcoded to two heads.** DLM finalizes every connector (3 messages each).
10. **The dock's pushes were being discarded.** Navarro frames some in the clear as wire sub `0x25`;
    `decode_in_lenient()` rejects anything that is not `0x45`, so they were logged as
    "invalid encrypted CP reply" and dropped — including the dock's ASCII firmware log.
    `cp::inner_plaintext()` + `cp::dock_trace_line()` now decode both, and vino logs `vino: dock: …`.

## Protocol recovered this session

### The video prologue (one transfer with the first frame)

```
type=2 sub=<stream>          32 B   body: <stream> 00 06 00 …
type=2 sub=<stream|0x10>     32 B   body: <stream|0x10> 00 06 00 …
type=4 sub=<stream> aux=0x0e 336 B  sealed, seq=0    <- pipe descriptor (304 B plaintext)
type=2 sub=<frame sub>       32 B   body: <frame sub> 00 00 00 …
type=4 sub=<frame sub> aux=0x04  32 B unsealed: 0a 00 04 <slot> 00 00 <ring(slot)> 00 00 <ring(prev)>
type=4 sub=<stream> aux=0x0e 1136 B sealed, seq=19   <- decoder config (1104 B plaintext)
… image records: type=4 sub=<connector << 3> aux=0 …
```

The two sealed records share the video block counter, so the configuration starts at `304/16 = 19`.

### The pipe descriptor is generative

14-byte marker, six `[len=0x002c][kind=0x000e][slot]` records of 40 configuration bytes each
(records advance by `len + 2`), then a 14-byte host-random tail. Fixed by twelve records across two
independently keyed connectors, and **stable across two separate sessions**, so these are constants
rather than per-session allocations:

| field | at | rule |
|---|---|---|
| slot id | record | `connector * 8 + index`, `index` 0..5 |
| ring | `cfg[12]` | `0x6fcc - slot * 0x21c` |
| plane 0 | `cfg[18]` | `0x71fb9000 - (connector * 6 + index) * 0x5000` |
| plane 1 | `cfg[26]` | `0x72166000 - (connector * 6 + index) * 0x8000` |

⭐ The dock confirms this layout in its own `id=0x4c` capability blob: a slot stride of `0x10e0` at
offset 60 and a step of `0x021c` at offset 64 — `0x10e0 = 8 * 0x21c`.

### The decoder configuration is Ridge's message

`video_arm::build_with_layout_word(2560, 1440, 0x2100, tail)` reproduces DLM's 1104-byte plaintext
**exactly**. Only the repeated layout word differs from Ridge's `0x4000`; its derivation from the
mode is not established, so it is pinned to the one observed mode.

### Frames cycle three ring slots

A frame closes with **two** 32-byte records, not Ridge's three:

```
type=4 sub=<frame sub> aux=0x0006   08 00 05 <slot>      00 00 <ring(slot)> 00 <frame no> …
type=4 sub=<frame sub> aux=0x0004   0a 00 04 <next slot> 00 00 <ring(next)> 00 00 <ring(slot)> …
```

The slot advances `index 0 -> 2 -> 4 -> 0`, so a head cycles three of its six buffers, and the
prologue's unsealed record opens the cycle at index 0 with index 4 as predecessor. Frame numbers
are a wrapping one-based `u8`. This is the same three-slot phase Ridge already tracks.

### Image record and strip layout

* Strips begin at record payload offset **0** — there is no per-record header. 72 strips of 54
  bytes fill a 4048-byte record exactly.
* A strip is `[u16 len][01 28][x u16][y u16][00 00 00 00][coded data]`.
* Grid is 20 × 180 at 2560×1440 — **128 px wide by 8 rows** — raster within a band, bands
  interlaced.

### A frame carries far more than image records

Over ~19 frames on connector 1, per frame DLM sends about four `aux=0` image records **and one
record each of `aux` = 2, 4, 6, 8, 0x0a, 0x0c, 0x0e**, plus a small sealed record back on the
*stream* sub (`0x000f`, 128 or 144 bytes, `aux=0x000c` or `0x0002`). One of them, `aux=0x0008`, is
3984 bytes of `06 01 0f 20 00 00 <frame sub> 00` followed by zeros, about 83% of the way through the
frame. **vino sends none of these**, and none is decoded.

## The live question

Every byte vino emits matches DLM. The first image record is byte-identical to one the dock
accepted from DLM. So the fault is **state, not bytes**: the dock does not believe the stream is
open, and the most likely reason is that it never accepted the sealed prologue's MAC — which would
mean vino's per-connector video key is not the key the dock derived.

⛔ **The `rrx` theory is tested and DEAD.** It looked compelling — the control plane works and only
video is broken, and those differ exactly by the per-connector keys — but both halves check out:

* Navarro **does** push a fresh `AKE_Send_Rrx` per connector: five in the session, at t=14.101,
  14.409, 14.672, 14.934 and 15.195 of the modeset capture. ⚠ The main link's push is
  **plaintext-framed** (`wsub=0x25`) while the **four per-connector ones are sealed** (`wsub=0x45`)
  — the opposite way round from what `navarro.md` §3 implies. `cp::perhead_rrx()` handles both, and
  reads the msg-id at inner offset 9 and `rrx` at 10..18, which is correct for each framing.
* vino picks up a **distinct** `rrx` for every connector. Logged on hardware:
  `head 0 de3d23ba7ed11130`, `head 1 78fffbc81a849e00`, `head 2 ee70e9295319e9ca`,
  `head 3 d69194cbe5d2c035`.

⚠ Note for anyone re-reading inbound frames: the HDCP msg-id is at inner offset **9** for dock→host
frames in *both* framings, not at 27. Offset 27 is the *outbound* layout, and reading it on an
inbound frame yields plausible-looking nonsense — that is what made this look like a lead.

### Found and implemented, but not the cure

⭐ **DLM clears the endpoint halt on every video endpoint before its first frame.** Two control
transfers about 2.4 s ahead of video in the modeset capture:

```
bmRequestType=0x02 bRequest=0x01 wValue=0x0000 wIndex=0x0008   CLEAR_FEATURE(ENDPOINT_HALT), EP 0x08
bmRequestType=0x02 bRequest=0x01 wValue=0x0000 wIndex=0x000a   CLEAR_FEATURE(ENDPOINT_HALT), EP 0x0a
```

vino only cleared the halt *after* an error. It now clears it when the persistent video queue is
opened, which also resets the endpoint's sequence number. Correct and measured, but the dock still
halts on image records, so it is not the cause on its own. Keep it.

### ⚠ An ambiguity worth resolving before trusting the stream-open sub

vino currently sends the 48-byte open on `stream_id | 0x10` (`0x17` for connector 0). That came
from the only two opens ever captured, on subs `0x17` and `0x1f`, attributed to "head 0 (`0x08`)"
and "head 1 (`0x0a`)" by endpoint. But **`0x17` and `0x1f` are also connectors 2 and 3's own stream
ids**, and the prologue that followed 4 s later in that same capture is on sub `0x0007` and does
*not* authenticate under either captured key — which is exactly what you would see if those opens
belonged to connectors 2 and 3 while the prologue belonged to connector 0.

So the open's sub is either `stream_id` or `stream_id | 0x10`, and the capture cannot separate them.
⚠ Both have been tried on hardware and both are accepted (URB status 0) and both still end in the
image records halting, so this is not the blocker — but do not treat `| 0x10` as established.

⊙ **So the question is still open**, and it is sharp: the dock accepts the stream-open and the whole
pipe configuration, then halts on an image record that is byte-identical to one it accepted from
DLM. Remaining candidates, none yet tested:

1. **The per-frame control records vino never sends** — one each of `aux` = 2, 4, 6, 8, 0x0a, 0x0c,
   0x0e on the frame sub, plus a 128/144-byte sealed record on the stream sub. In DLM's frame these
   sit *after* the first image records, so they cannot explain a halt on the first one — unless the
   dock requires the set to have been seen once before it will accept any frame at all.
2. **Whether the dock is accepting the sealed prologue's MAC at all.** URB status 0 only proves the
   bytes were taken. If the pipe configuration is being silently dropped, the image records arrive
   with no pipe and the halt follows. A way to distinguish: send a deliberately corrupted MAC and
   see whether anything observable changes.
3. **`compute_eks` / `V` for a connector.** Proven on Ridge, whose per-head video works, so this is
   lower probability — but Ridge's per-head burst was misframed once before and the symptom then
   was also "control fine, video dead".

### Ruled out by test — do not re-chase

* The stream-open: content, length, sub, key, nonce, and being its own transfer. Status 0.
* The pipe descriptor and decoder configuration: byte-identical, and accepted (status 0).
* Dock-side addresses being a per-session allocation: identical across two separate sessions.
* Record packing, record size, `aux`, strip geometry, band order: all now match DLM byte-for-byte.
* Prologue inline with the pixels vs. in its own transfer: both halt identically.
* Waiting 4 s after the stream-open, as DLM does: no change.
* Transfer size: a 17,856-byte transfer halts the same way a 204,064-byte one does (though the
  smaller one does not make the dock re-enumerate, so quantity affects severity, not acceptance).
* Driving empty connectors: fixed, and not the cause.
* The per-connector `rrx`: present, distinct, and correctly extracted — see above.
* Clearing the endpoint halt before streaming, as DLM does: implemented, no change.
* The stream-open's sub: both `stream_id` and `stream_id | 0x10` accepted, both still halt.

### Tools written this session

All under `/tmp` scratch, worth re-creating if useful — the durable ones are the analysis recipes:

* Decrypt any Navarro control capture with the **Dl3Cmac tag as the oracle** (never a plaintext
  shape). Candidate `(key, nonce)` pairs come from the frida `krs` dump; the CTR nonce is the
  recorded one, the MAC nonce is it with `byte0 ^ 0x80`.
* Walk video records: `[00 00][size u16][type u32][sub u16][aux u16][seq u32]`, stride `size + 4`.
* Authenticate a sealed video record with a connector's key/nonce to recover its plaintext.
